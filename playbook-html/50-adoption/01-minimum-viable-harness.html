The Minimum Viable Harness

Don't wait for the perfect harness — stand up the smallest one that already closes the loop. One guide file, a formatter and linter, a type check, a gate that blocks on red, and one real behaviour test. You can build it in week one, and it beats a grand plan you never finish.

We've covered what works, and the entire rogues' gallery of what doesn't. Which leaves the only question that matters on a real Monday with a real deadline: where do you actually start? Not with the full layered harness this book spent twenty pages describing — that's the destination, not the on-ramp. This page is the on-ramp: the five smallest pieces that still close the loop. A scrappy harness that exists beats a magnificent one that's still a plan.

01The principle

A minimum viable harness is the smallest set of controls that still does the whole job: shape the work before the agent acts, grade it after, and refuse to let red merge. Everything earlier in this playbook describes a full harness. This page is the on-ramp: what you put in place on day one, before the codebase even has a shape, so the very first agent-written change lands inside a loop instead of outside one. Five pieces, one of each kind that matters:

  1. One guide file — a single checked-in agent instruction file (CLAUDE.md, AGENTS.md) holding where the code lives, the non-negotiable conventions, and the exact commands to build and test. This is your feedforward.
  2. A formatter and a linter — the cheapest sensors there are. They catch style drift and a class of obvious mistakes deterministically, in milliseconds, with no judgement call.
  3. A type check — if your language has one, the single highest-signal free sensor you will ever get: a proof, run on every change, that whole categories of bug cannot be in the diff. If your language is untyped, skip this and lean harder on the test.
  4. A gate that blocks on red — a pre-push hook (or the earliest stage you can enforce) that runs those checks and refuses the push when any fail. A check that only warns is not a gate.
  5. One real behaviour test — a single end-to-end test that proves the app's one most important thing actually works. Not a test of what the code does — a test of what the product needs. This is the seed of your behaviour harness, and it's the piece teams skip first and regret first.

Notice what's not on it: no fitness functions, no mutation testing, no AI reviewer, no design guide, no CI matrix. Those are all real, and they all come later (the next page is about adding them). Week one is about getting one of each control type working end to end, not getting any of them complete.

02Why it works

A harness is only a harness when the loop closes — feedforward shapes the attempt, a sensor grades it, and a gate enforces the verdict. Miss any one of the three and you don't have a small harness, you have no harness:

The minimum viable harness is the smallest configuration where all three are present at once

Guides, no gate

A suggestion box

The agent reads your conventions, ignores half under pressure (it doesn't reliably self-follow rules), and nothing stops the result.

Sensors, no gate

A dashboard nobody reads

The linter is red, the build is broken, and the change merges anyway — because failing was never blocking.

Gate over nothing

A green check that proves nothing

The gate blocks on a vacuous sensor that passes whether or not the work happened.

Drop any one leg and the loop doesn't close — three half-harnesses, zero whole ones

The minimum viable harness is weak — one behaviour test covers one path, the linter misses semantic bugs — but it is whole. And a whole-but-weak loop is the thing you can actually improve, because the steering loop that grows a harness needs a harness to grow: you watch it miss something, you add the guide or sensor that would have caught it, you re-run. You can't steer a loop that doesn't exist yet.

There's a second reason to start small, the same lesson as keeping a hook fast enough that nobody skips it: a harness the team actually adopts beats a bigger one they route around. A five-line guide file gets read and kept current; a five-page one goes stale and gets ignored. And there's a timing argument: an empty new repo is the cheapest moment you will ever have to do this. Harnessability is something you bank early or pay for forever.

Minimum viable isn't a compromise you'll grow out of — it's the only version that survives contact with a real team under a real deadline.

03How to apply it

Work the checklist top to bottom. Each item is one sitting, and the whole thing is a day, not a sprint.

  • Write the guide file first, and keep it short. Repo layout in a few lines, the conventions you refuse to compromise on, the literal build and test commands. The test for every line: would the agent get this wrong without it? If not, cut the line — a bloated guide file is a tax paid on every task. A skeleton:
# <Project> — agent guide

## Layout
- app code: <where>
- tests: <where>
- specs/contracts: <where>

## Conventions (non-negotiable)
- <the 3–5 rules you will not bend>

## Commands
- build:  <command>
- test:   <command>
- check:  <lint + types + test, the one command the gate runs>

The whole guide file — short enough to stay read and kept current

  • Wire the formatter, linter, and type check as one command. Make a single entry point — call it check — that runs all three and exits non-zero if any fail. One command is what the guide file points at, what the gate runs, and what a human runs by hand.
  • Put the gate at the earliest stage you can enforce, and make it block. A pre-push hook is the usual sweet spot. The non-negotiable property is that a failing check fails the push — warn-only is not a gate. (When you add CI later, the authoritative gate moves there, where it can't be bypassed with a local flag.)
  • Write one behaviour test against the spec, not the code. Pick the single most important thing the product must do and prove it end to end — and assert the observable end-state, never just "it ran without throwing." Add it to the check command so the gate runs it too.
  • Do: keep every piece small enough to finish in week one; make the gate block, not warn; point the guide file at the same check command the gate runs.
  • Don't: wait for the "real" harness before shipping the first feature; pile every check you can think of onto day one (you'll learn what this repo needs by watching it fail); skip the behaviour test because lint and types are "probably enough" — they check the code is clean, never that it does the right thing.

04In practice

Two teams start the same new service in the same week.

Team A

Ship first, harness later

  • The agent is pointed at an empty repo with a one-line prompt. It's fast and feels great.
  • By week two: forty files, no guide file, no gate, a linter nobody runs — and three different ways to talk to the database, because nothing rejected the wrong ones.
  • The first real bug returns the wrong total; it passes review because it looks right and there's no test that would have caught it.

Now comes the expensive version of every week-one task — retrofitting types onto forty files, reconciling three conventions. The harness arrives as cleanup instead of scaffolding.

Team B

Day one on the minimum viable harness

  • Before the first feature: a short guide file, format-lint-type wired into one check, a pre-push hook that blocks on red, one end-to-end test.
  • The agent reads the conventions on every task; the gate rejects the pushes that ignore them. The database is talked to one way from the first commit.
  • When a feature returns the wrong total in week two, the behaviour test goes red before the push lands.

Not slower for the day they spent — faster by week two, because every change landed inside a loop that caught its own mistakes.

The harness isn't overhead you add once there's a mess — it's what keeps the mess from forming

The lesson the example carries: the cost of standing up the minimum viable harness is a day at the start. The cost of skipping it is paid back, with interest, as cleanup — and some of it (the conventions that diverged, the bug that shipped) you don't get to pay back at all.

05Anti-patterns

  • The someday harness. Waiting for the perfect, complete setup before standing up any of it — so it never ships and the first agent PRs land completely ungated. Small and whole beats big and someday.
  • The big-bang harness. The opposite mistake — wiring fitness functions, mutation testing, an AI reviewer, and a full CI matrix on day one. It stalls and it's over-engineered for a repo with no shape yet. Ship one of each control type; grow the rest.
  • The half-loop. Guides with no gate (a suggestion box), or sensors with no gate (a dashboard nobody reads). All three — feedforward, sensor, gate — or it isn't a harness.
  • The decorative gate. A hook or check that runs and warns but doesn't block, so red still merges. A gate that can't say no is set dressing.
  • The lint-only start. Format, lint, and types but no behaviour test — so the harness proves the code is clean and never once proves it does what the product needs. The behaviour test is the piece hardest to add later and easiest to skip now.
