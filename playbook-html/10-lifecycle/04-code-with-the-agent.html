Code With the Agent

Steer with the concrete thing, not an analogy — "match this function" beats "do it like the other page." And never assume a rule you stated is a rule the agent followed: it drifts off clear instructions, so the enforcement has to live outside it, in sensors and review.

We've sliced the plan into bite-sized tasks, each with its own test. Now the agent actually starts writing — and this is where a lot of people make the same quiet mistake: they hit go, wander off, and come back to a finished diff. The diff is the most expensive place to discover the agent misread you.

This chapter is about staying in the room while it works — steering with the concrete thing rather than a hand-wave, and accepting the slightly deflating fact that telling an agent a rule and getting the rule obeyed are two very different events.

The governed lifecycle — you are here

01The principle

The slice is approved and the agent starts writing. Your job now isn't to step back and wait for the diff — it's to steer in the moment, and to not trust what you can't check. Two halves.

Steer with concrete reference

"Make it work like the accounts list" forces the agent to guess what like means — and it guesses the most probable thing. Instead quote the exact behaviour: point at the file and lines, paste the rule. Then watch it work and course-correct early — a nudge at the first wrong line is a sentence; the same fix ten files later is a rebuild.

Don't trust the agent to police itself

Putting a rule in front of the agent does not mean it follows the rule. It can't reliably hold every instruction in attention while solving the problem, so it drifts. Guides lower the rate of violations; they never drive it to zero. The enforcement lives outside the agent: sensors and review by a separate evaluator.

The two halves of coding with the agent — steer it in, then catch what slips

Steer with concrete reference, not analogy. A scoped, concrete instruction is to this in-the-moment loop what a concrete spec is to the whole feature: it removes the gap the agent would otherwise fill with a confident wrong guess. Be specific about the task itself — the inputs, the outputs, the files to touch, the files to read first. Then watch it work and redirect the moment it heads the wrong way.

Don't trust the agent to police itself. Not out of defiance — it simply can't reliably hold every instruction in attention while solving the problem in front of it, so it drifts off rules you stated plainly. So never rely on the agent enforcing its own constraints. The enforcement lives outside the agent: sensors — computational checks like type checkers, linters, and tests that fail loudly the instant a rule is broken — and review by a separate evaluator. Instructions are feedforward (what you tell the agent before it acts); sensors and review are feedback (what catches it after). You need both, because the first is unreliable on its own.

"But I told it not to" is neither a defence nor a fix — the only reliable enforcement is a check the agent cannot talk its way past.

02Why it works

"Like X" relies on the agent reconstructing your intent from an analogy, and it doesn't have your mental model of how X works — it has the most probable completion of the phrase "like X," which can be subtly or wildly off. Hand it the actual reference and there's nothing left to reconstruct: the gap where the wrong guess would go is simply closed.

Early correction is cheap for the same reason slicing and plan review are: a wrong direction compounds. Caught at its source it's a one-line redirect; caught after the agent has built three things on top of it, it's a thread you have to pull through all of them. Watching and nudging keeps every wrong turn small enough to fix in a sentence.

And the self-follow limit is structural, not a tuning problem you can prompt your way out of. The agent produces the next most probable step given everything in front of it; a rule you stated is one signal among many competing for its attention, and the local pull of "make this work" can simply outweigh it. It's the same reason verification can't be self-graded and review can't be done by the author: the agent's own word about its own compliance is the least reliable signal you have.

03How to apply it

  • Quote, don't gesture. "Match the validation in handleSubmit at orders.ts:40-58" beats "validate like the orders form." Paste the reference behaviour or the rule straight into the task.
  • Be specific and scoped. Name the deliverable, the inputs and outputs, the files to touch, and the files to read first. A scoped task is one the agent can hold whole — and one you can actually review.
  • Course-correct early and often. Redirect at the first wrong turn, not at the finished diff. You can stop the agent mid-action — that interrupt is a normal, expected part of steering, and it's the cheapest correction you have.
  • Send investigation to a side channel. For "go figure out how X works," use a subagent — a separate, scoped agent run — so the answer comes back without flooding your working thread. Keep the main thread's attention budget for the task.
  • Keep the agent on a leash you can see. Prefer a scoped, reversible working mode where consequential actions are approved deliberately, and keep diffs small enough to review.
  • Put rules where a sensor can enforce them. If a constraint matters, back it with a check — a type, a lint rule, a test — not just a sentence in a guide. State it as feedforward and enforce it as feedback.
  • Don't: say "like X does it" and hope; let a wrong direction run because interrupting feels premature; assume a rule in the prompt is a rule obeyed; or let the agent act unsupervised on anything you can't reverse.

04In practice

Take the per-user deal priority feature at slice 3 — extend the existing deals-list query to join the current user's priorities and order flagged-first.

Vague and trusting

"…like how we sort other lists, and remember flags are per-user"

  • "Like how we sort other lists" — the agent picks a list that sorts by a global column and mirrors that shape, which doesn't fit per-user data at all.
  • "Remember flags are per-user" — a rule, stated clearly — doesn't hold: deep in the join it drops the user_id filter because the simpler query still returns rows.
  • The local pull of make-it-run beat the rule you stated.

It hands you a green diff that leaks flags across users. You told it the rule; it didn't follow the rule.

Concrete and checked

Point at the exact thing, back it with a check

  • "Extend getDealsList in deals/queries.ts:120-145; left-join deal_priorities on (deal_id, current_user_id)… read the schema first." No analogy to reconstruct.
  • The privacy rule is backed by the two-user test (a sensor) and a reviewer who isn't the author.
  • Mid-stream you watch it begin the join without the user filter and redirect in one sentence.

The rule is honoured — not because you asked nicely, but because a check would have caught the violation if you hadn't.

Same slice, two prompts — specificity removes the guess, external checks remove the dependence on self-discipline

The lesson the example carries: specificity removes the guess, and external checks remove the dependence on the agent's self-discipline. Steer concretely, verify always, and never confuse "I instructed it" with "it complied."

05Anti-patterns

  • The "like X does it" prompt. Steering by analogy, so the agent reconstructs your intent from a guess and builds against the wrong reference. (Failure modes)
  • Trusting the agent to self-enforce. Assuming a rule stated in the prompt or a guide is a rule obeyed. The fix is sensors and review, not a firmer tone.
  • Late course-correction. Letting a wrong direction run all the way to the diff because interrupting felt premature — turning a one-line redirect into a rebuild.
  • The unsupervised agent. Letting it act across the repo on irreversible things with no scoped mode, no approval step, and no small diff to review.
