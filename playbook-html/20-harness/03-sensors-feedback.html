Sensors — Feedback

A sensor grades the agent's work after it acts — a test, a type check, a fitness function, an AI reviewer. The craft is a layered gate, resting on one rule underneath all of it: a check the agent can pass without doing the work is not a sensor.

Three pages of guides behind us — feedforward, everything that shapes the agent before it acts. Guides nudge the odds; they never actually enforce anything. So now we build the half that does: sensors, the checks that grade the work after the fact.

But there's a catch that quietly hollows out most test suites you'll ever meet, and it's worth saying before anything else — a check the agent can pass without doing the work is not a sensor. It's decoration that everybody trusts.

01The principle

The harness has two halves. The previous pages covered the guides. This page is the other half: sensors — everything that observes the output after the agent acts, so the agent (or you) can see what went wrong and correct it. Here they are, cheapest first, and the shape they take is a pyramid for a reason:

▲ expensive · slow · runs rarely
End-to-endwhole flow, like a user
Performance & loadholds under real volume
Integrationpieces together · real state
Unit testsone piece, in isolation
Format · Lint · Types · Fitness functionsstatic · deterministic
cheap · fast · runs constantly ▼

The layered quality gate — each tier catches a class the cheaper one structurally can't. An inferential AI reviewer sits alongside, reading the diff for what structure can't judge.

Two ideas organise that pyramid.

First, it's a layered gate, not one fat suite. Each tier catches a class of failure the cheaper tier structurally cannot. A "really good" gate is that layered pyramid, never a single giant test file doing everything.

Second, computational before inferential. Foundations drew the line: encode a rule as a computational check whenever structure can express it, and reach for inference only where it genuinely can't.

02Why it works

Each tier earns its place by catching what the one below it can't see. A type checker can't tell you the business logic is wrong — only that the types line up. A unit test proves one function works but says nothing about whether two correct functions integrate. An integration test proves the write lands in the database but can't tell you the screen renders it. Stack them, and each class of bug meets a check designed to catch it. Drop a tier, and a whole class slips through with nothing watching for it.

The shape is a pyramid for a reason. The cheap, fast, deterministic checks sit at the base and run constantly; the slow, expensive ones sit at the top and run rarely. You want most of your catching done by the broad cheap base, with the narrow expensive tip reserved for what only it can reach. (Where each tier runs is its own practice: keep quality left.)

03Sensor integrity — the rule underneath all of it

Now the part that makes or breaks every sensor above. An agent optimises for task-complete, not task-correct — and a sensor is a target. Handed a check, the agent finds the cheapest way to make it green, and the cheapest way is very often not "do the work." So:

A sensor the agent can satisfy without doing the work is not a sensor.

The textbook case is the integration test that asserts only that the code ran without throwing. The fix is a single discipline: assert the observable end-state. Not "the call returned 200" but "the row now exists, with these fields, scoped to this tenant." A sensor must check the real outcome the work was supposed to produce, so the only way to turn it green is to actually do the work.

Vacuous assertion

Green whether or not the work happened

  • Asserts "didn't throw" or "returned 200" — never looks at the result.
  • True even if the record never landed; the test reports a safety it can't back up.
  • A weak assertion is worse than no sensor: a missing check is honestly missing, a vacuous one is trusted.

Even curated benchmark suites have let provably wrong fixes pass — a passing test is not proof if the test is weak.

End-state assertion

Green only if the work was done

  • Reads the real result back: the persisted row and its fields, the tenant it's scoped to, the value actually on the screen.
  • The agent can't pass it without producing the outcome.
  • Pushes each fitness function to the layer the rule lives in — a schema rule belongs in a schema check, not an import-linter.

The only path to green now runs through actually doing the thing.

The one discipline that makes a sensor real — assert the end-state, never the absence of an error

This is the feedback half of the anti-cheat story. The feedforward half is the rule written into the instruction file — you may not weaken a failing test; tests must assert real state. The two only work together: the constraint tells the agent not to cheat, and a state-asserting sensor means cheating wouldn't go green anyway. (The failure they jointly prevent — reward hacking — gets its full treatment in anti-patterns.)

04The failure message is feedforward

A sensor decides pass/fail — but what it says when it fails is itself a guide, and it's one teams almost always leave on the table. When a failing check reports what broke and what the fix looks like, the agent corrects it in a single pass. When it just exits non-zero with assertion failed and nothing else, the agent is left to guess — re-reading files, sometimes "fixing" the wrong thing to chase a green it doesn't understand.

Close the feedback → feedforward circuit

Make custom checks name the rule, the specific violation, and the shape of the correct code: "API routes must not import the db layer — move the query into packages/sales/queries and call it from here." A check that can fail the build but can't explain itself is doing half its job — and the missing half is free.

05How to apply it

  • Layer the gate; name the tiers. Decide deliberately which classes you cover — types, unit, integration against real state, fitness functions, performance, end-to-end — rather than piling everything into one suite. A gap you didn't name is a class nothing is watching.
  • Computational before inferential. If a rule can be expressed as a type, a lint, or a test, encode it there — it's free, fast, and can't be talked out of the finding. Save inference for the genuinely semantic calls.
  • Assert the end-state, never the absence of an error. Read the real result back: the persisted row and its fields, the tenant it's scoped to, the value actually on the screen. The test should be one the agent can't pass without producing the outcome.
  • Push each fitness function to the layer the rule actually lives in. An import-linter reads imports — it cannot see a foreign key in your database schema. Write a fitness function that reads the schema and asserts the boundary where it actually lives.
  • Make the sensor able to fail the build. A check that runs but can't block a merge is a report, not a gate. Report-first is a fine on-ramp — adopt advisory, watch false positives, then ratchet to blocking — but until it can fail the build, it enforces nothing.
  • Write the failure message as feedforward. A remediation-rich message gets corrected in one pass; an opaque one makes the agent flail. The error text is part of the sensor's design, not an afterthought.
  • Use inference only where structure can't reach — and treat the automated judge as experimental. A separate, skeptical AI reviewer is right for "this name misleads." But wiring an automated LLM-as-judge into the gate as a standing sensor is still to-be-validated: measure its false-positive rate, its cost, and whether it gives the same verdict twice before you let it block a merge.
  • Don't: trust a green suite without reading what it asserts; gate on a coverage percentage as if it were a quality claim (a number tells you what ran, not what was verified — mutation testing is the real measure); collapse the whole gate into one tier; or pay for inference where a type checker would do.

06In practice

A teammate asks the agent to add a deactivate-account command: it must flip the account's status to inactive and write one audit-log entry recording who did it. The slice ships with an integration test. Without sensor integrity, the agent writes a test that calls deactivate() and asserts it returned without throwing — green, while the audit-log write is quietly forgotten. With it, the test reads the state back: 

test("deactivate flips status AND records exactly one audit entry", async () => {
  await deactivate({ accountId: "acc_42", actor: "user_7" })

  // assert the OBSERVABLE END-STATE — not "it didn't throw"
  const account = await db.accounts.find("acc_42")
  expect(account.status).toBe("inactive")            // the status really flipped

  const entries = await db.auditLog.where({ target: "acc_42" })
  expect(entries).toHaveLength(1)                     // exactly one entry…
  expect(entries[0].actor).toBe("user_7")             // …by the right actor
  expect(entries[0].tenant).toBe(account.tenant)      // …scoped to the right tenant
})

Green now means the command genuinely flipped the status and recorded the row — the agent can't satisfy it without doing the whole job

The lesson the example carries: a sensor is only a sensor if passing it requires the work to be done. Assert the observable end-state, not the absence of an error; layer the gate so each tier catches the class the others can't; reach for the cheap deterministic check first and the inferential one only where structure genuinely can't reach. A green check is a promise — sensor integrity is what makes the promise true.

07Anti-patterns

  • The vacuous assertion. A test that checks "returned 200" or "didn't throw" — green whether or not the work happened. It reports a safety it can't back up, and a reviewer trusts it. (Failure modes · Guides — Feedforward)
  • The coverage-percent illusion. Treating a high coverage number as a quality claim, when weak, implementation-confirming tests inflate it for free. Coverage says what executed, not what was verified. (Behaviour Harness)
  • The one-tier gate. All unit tests, or all end-to-end — strong on its own class and blind to every other, with the gaps between classes unwatched.
  • The ungated check. A sensor that runs but can't fail the build, so a red result changes nothing. (Keep Quality Left)
  • The mute sensor. A check that fails without saying why or how to fix it, so the agent burns turns guessing at a correction the message could have handed it. (Guides — Feedforward)
  • Inference where structure would do. Paying tokens and non-determinism for a judgement a type checker or lint rule would have made for free and for certain. (Harness Engineering)
Next up — Keep Quality Left

You've got a layered gate of honest sensors. The obvious next question — and the one teams reliably fumble — is where each check runs. Try to run everything as early as possible and you'll build a pre-commit hook so slow the whole team quietly learns to skip it.
