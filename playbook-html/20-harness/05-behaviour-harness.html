Behaviour Harness

The hardest harness to build is the one that proves the code does what the business wanted. The lever is the invariant: bind a test to the rule rather than to the code the agent wrote, and you escape its favourite failure — tests that merely confirm the implementation.

Foundations named three things a harness regulates, hardest last: is the code clean, is it the right shape, and — the genuinely brutal one — does it do what the business actually wanted? The first two you can check against the code itself. The third you can't, because the code is the agent's answer to that question, and asking the agent to test its own answer is exactly how you end up with a suite that's a mirror, not a check.

This page is the way out, and it hinges on one word: bind the test to the invariant, not the implementation.

01The principle

Foundations named three things a harness regulates, hardest last. The first two pages of concrete sensors mostly served the first two categories. This page is the third — and it's the hard one, still unsolved for high-autonomy work, the reason a human stays in the loop.

A linter reads the code and tells you. Checkable against the code itself.

Architecture fitness — is it the right shape?

A fitness function reads the dependency graph and tells you. Still checkable against the code.

vs the code

Behaviour — does it do what the business wanted?

Can't be answered from the code, because the code is the agent's answer. The hard one — and the whole of this page.

needs intent

Three things a harness regulates, hardest last — only the third needs a source outside the code

Here's what makes it hard. Handed the job of testing its own work with only that code in context, the agent reverse-engineers a test from the code it just wrote, so the test proves the code does what it does — never what the business needed. A green suite built that way is a mirror, not a check. The cure is not to distrust every agent-written test — it's to change the source the test is derived from: give the agent the spec or the invariant, not just the code, and it writes a test that can actually disagree with the implementation.

The tool for that is the invariant: a statement of what must always be true for a scenario, no matter the input or the implementation. "After any transfer between accounts, the total money across all accounts is unchanged." "A posted invoice can never have a negative line total." An invariant is a property of the problem, so a test built from it is bound to the business rule — it can't silently encode the code's current bug, because it was never derived from the code.

The practice that operationalises this names each scenario and pins its invariant:

  • Name the scenario. Give each behaviour contract a stable identifier — an SCN (a scenario id, e.g. SCN-LEDGER-014). The test cites the scenario, not the function.
  • State its invariant precisely, in business language, and have the person who owns the intent — a domain owner, not the implementer — approve it. That approved description is the contract the behaviour test proves.
  • Trace it both ways. Every approved scenario must have a test; every test must cite a real scenario. Then a dropped contract is visible instead of silently going uncovered.

A test is only as honest as the thing it's derived from.

02Why it works

Derive a test from the code and it inherits the code's bugs; derive it from the invariant and it stands outside the code, able to disagree with it. That's the whole move — and two techniques sharpen it, each attacking the confirms-the-implementation failure from a different side.

Derived from the code

A mirror, not a check

  • The agent reverse-engineers the test from the happy path it just coded.
  • It asserts exactly what the code does — so it passes by construction.
  • The branch the code gets wrong is the branch the example never touches.

A green, high-coverage suite that verifies nothing the code didn't already claim.

Derived from the invariant

A check that can disagree

  • The property comes from the problem — "money is conserved" — not the function body.
  • A tool generates hundreds of inputs, including the weird edges no one typed.
  • The invariant fails on the overdraw case the agent never hand-wrote.

The bug surfaces before merge, from a test that stands outside the code.

Same agent, same code — change the source the test is derived from, and it gains teeth

Property-based testing changes how the test gets its inputs: you assert the invariant and let a tool generate hundreds of inputs, so it catches the case the agent's hand-picked example skipped. Mutation testing tests the tests themselves: it injects small deliberate bugs — flips a < to <=, deletes a line — to produce a "mutant," then reruns the suite. A killed mutant means the suite noticed; a surviving mutant is proof, in one concrete example, that your tests would not have caught that bug. This is the empirical answer to the coverage illusion.

Put them in a loop and they compound — and killing a named surviving mutant is a task the agent is genuinely good at

03How to apply it

  • Start from the invariant, not the example. For each scenario, ask "what must be true here no matter the input?" and write that down. The example test comes second, if at all — the invariant is the contract.
  • Name and pin each scenario; bind the test to the name. Give every behaviour contract a stable id, cite it from the test, and keep the trace bidirectional so a missing test is loud, not silent.
  • Let the person who owns the intent approve the contract. The domain owner signs off on the invariant, independently of whoever (or whatever) implements it — so the test proves the business's need, not the implementer's guess at it.
  • Use property-based tests for invariants you can state. Assert the property; let the tool generate the inputs; ground the property in the spec's semantics (docstring, types, names), never in the function body.
  • Grade the suite with mutation testing, not coverage. Run it on the high-value modules, treat a high coverage number with surviving mutants as the warning it is, and feed the survivors back to the agent to kill.
  • Make UI quality gradable. Check in design tokens so "looks right" becomes a named-value match, and capture an evidence image on the passing run so a reviewer sees the real rendered screen — not a green check that only proves a locator resolved.
  • Keep the human on the question of intent. A behaviour harness can prove the code satisfies the invariant; it can't prove the invariant itself is what the business meant. That call stays with a person — and a separate, skeptical reviewer grades the result against the spec rather than letting the author self-certify.
  • Don't: let the agent write the behaviour test from the code it just wrote; treat a coverage percentage as proof of behaviour; or treat a green structure-only UI test as proof the screen is actually right.

04In practice

A teammate asks the agent to build transfer(from, to, amount) — move money between two accounts. Without the behaviour harness, the agent writes its own test from the happy path it coded: transfer $100, assert A dropped $100 and B rose $100. Green — but the code has a bug: on a transfer that would overdraw from, it deducts the full amount but silently caps the credit to B, so the difference vanishes. The clean-$100 example never touches that branch. With the behaviour harness, the scenario is named and its invariant approved before code is written: 

// SCN-LEDGER-014 — money is neither created nor destroyed
//   approved by the domain owner, before any code
property("sum of all balances is unchanged after any transfer", () => {
  forAll(accounts(), transfers(), (opening, txns) => {
    const closing = applyAll(opening, txns)
    return total(closing) === total(opening)   // conservation — independent of the code
  })
})
// the tool generates hundreds of transfers, including the OVERDRAW case
// nobody hand-wrote → the property fails on it → the bug surfaces before merge

The conservation property is derived from the rule, not the code — so it catches the branch the agent's example skipped

Then mutation testing runs on the module: it flips the sign on the deduction, the property test catches the mutant — confirming the suite has real teeth — while a surviving mutant in a rounding helper the property didn't cover is handed to the agent, which writes the assertion that kills it. And because the balances also render on a screen, a captured evidence image on the green run lets the reviewer see the figures are right, not just trust the DOM had numbers in it.

The lesson the example carries: the behaviour harness works by binding the check to the business rule — the invariant, named as a scenario and owned by the domain — instead of to the code the agent wrote. Property-based testing derives the test from the rule and generates the inputs that break it; mutation testing proves the suite can catch a bug at all; evidence images make subjective UI gradable; and a human still owns the one thing none of it can settle — whether the rule is what the business actually meant.

05Anti-patterns

  • The confirms-the-implementation test. A test reverse-engineered from the code it's meant to check, so it proves the code does what it does — not what was needed. The failure this whole page exists to prevent. (Sensors — Feedback · Failure Modes)
  • The coverage mirage. High coverage, surviving mutants — a suite that executes everything and verifies nothing. Mutation score measures the right thing. (Sensors — Feedback)
  • The unowned contract. A behaviour test with no domain-approved invariant behind it, so nobody ever confirmed the rule it checks is the business's actual intent. (Spec — The Contract)
  • The DOM-only "looks right." Treating a passing structure-only UI test as proof the screen renders correctly — no evidence image, no design-token grading — so a visually broken but DOM-intact page ships green. (Verify — Proof, Not Vibes · Guides — Feedforward)
  • The closed loop on intent. Letting the harness convince you the behaviour question is settled, with no separate human check that the result is what the business meant. (Responsible Team and AI Debt)
