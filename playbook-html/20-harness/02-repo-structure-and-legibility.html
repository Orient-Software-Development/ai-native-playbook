Repo Structure and Legibility

How your repo is laid out is a guide. A predictable, conventional structure is feedforward the repo broadcasts for free, on every task, without spending a token to re-explain itself.

Last page covered the guides you sit down and author — instruction files, blueprints, constraints. This one is sneakier, because the most powerful guide in your repo is one you never actually write. It's the layout.

Before the agent reads a single word you wrote, it reads the folder tree, the file names, where everything sits relative to everything else. A tidy, conventional structure is feedforward the repo broadcasts for free, on every task, forever. A bespoke mess is a maze it has to grope through one file at a time.

01The principle

The agent perceives your project entirely through its context window. Before it reads a single guide you authored, it reads the repo — the folder tree, the file names, where things sit relative to each other. That layout is the first feedforward the agent ever meets, and it's the cheapest you'll ever own: you arrange the structure once, and every future task benefits without you re-spending a token. A legible repo — one a newcomer could navigate and reason about on its own — is a map. An illegible one is a maze the agent has to grope through file by file, guessing as it goes.

Illegible — a maze

No convention to lean on. Every placement is a guess; the agent burns its budget just locating things.

Legible — a map

Matches the ecosystem's priors. The agent's defaults are already right, and it navigates instead of searching.

The same project, two structures — one the agent reads as a map, one it gropes through as a maze

Legibility isn't a vibe; it's a small set of concrete arrangements:

  • A conventional, industry-standard layout. Lay the project out the way its framework and ecosystem expect. Agents carry strong priors about where things should live; when your structure matches them, half the map is drawn before you start. A bespoke layout throws all of that away.
  • A dedicated home for the contracts. Keep specs in one obvious, named place (a specs/ folder), not scattered through wikis, tickets, and comments. The contract the agent builds against has to be findable to be useful.
  • Sensors co-located with the code they guard. Put each test beside the module it covers, not in a far-off mirror tree. When the agent opens a module it sees the test that proves it, so it extends the suite instead of leaving the new path uncovered.
  • Clear package and module boundaries. Make it obvious what lives where and which direction dependencies may flow, so the agent extends the structure instead of reaching across a line it shouldn't.
  • Consistent naming. When the same kind of thing is named the same way everywhere, the agent can predict a file's name from its job and find it without a full-tree search.

A legible repo turns "the agent can't find it" into "the agent navigates it."

02Why it works

The agent fills every gap it meets with its most probable guess (the same mechanism behind every guide — see feedforward). A legible repo simply leaves fewer gaps to fill. When the layout matches convention, the agent's default placement is correct. When the test sits beside the code, the agent finds it and extends it rather than inventing a parallel one. When the boundary is explicit, the agent doesn't reach across it, because it can see the line.

There's a budget reason too. In an illegible repo the agent burns its attention budget just locating things — grepping the tree, opening wrong files, reconstructing a structure that was never written down. Every one of those tokens is spent on navigation instead of on the task, and the agent reasons worse for it.

This is the harnessability idea made concrete, and it pays off the same way: twice. Clear boundaries, conventional layout, and tests beside their code were always good engineering — they make the repo easier for humans. The same arrangements now make it easier for agents. You're not doing new work to be agent-ready; you're doing the work you'd do anyway, and collecting a second payoff.

03How to apply it

  • Follow the conventional layout for your stack. Use the directory structure your framework and package manager expect, named the way the ecosystem names it. Save your creativity for the product, not the scaffolding — every deviation is a guide you now have to write by hand.
  • Give the contracts one obvious home. A top-level specs/ folder, one file per spec, named predictably. The agent should never have to ask where the spec for a feature lives.
  • Put sensors next to the code. Co-locate tests with the modules they cover. Proximity is itself a signal: it tells the agent (and the reviewer) that this code is the thing this test is responsible for.
  • Make boundaries a readable map, not just a buried config. This is the one teams get wrong most often. The rule "package A may not import package B" usually does exist — encoded deep in a hundreds-of-lines lint config. But that config is a sensor: it enforces the boundary after the agent crosses it. Give the agent a short, human-readable map alongside the config that enforces it.
  • Name things predictably. One naming pattern per kind of thing, applied everywhere, so a file's name is derivable from its role.
  • For a large codebase, give the agent a structural index it can query. Hand the agent a code graph — a machine-generated index of the symbols and how they connect — that it queries directly instead of grepping the tree file by file. Treat this as a general practice, not an endorsement of any one indexer.
  • Don't: invent a bespoke layout the agent has no priors for; scatter conventions across a wiki, three docs, and a config; let a giant lint config be the only record of your architecture; or let the structure drift until the layout no longer reflects how the code works.

04In practice

A teammate asks the agent to add a feature spanning two packages of a monorepo — a reporting view that needs a number computed in the finance package. The repo enforces a strict rule: finance may not depend on reporting. That rule is real, and it's enforced — by a long, generated lint config that fails the build on a forbidden import.

Without legibility

The boundary is enforced, but never stated

  • Nowhere is there a plain-language map of which package owns what — the only record is the lint config, which no agent reads front-to-back to learn the architecture.
  • So the agent guesses: it puts the computation in reporting and imports finance the wrong way — plausible, and exactly backwards.
  • The build goes red on a rule it never saw stated. It moves a file, trips a different line of the same config, and thrashes.

The boundary was enforced but never legible, so the agent learned it the most expensive way possible — one red build at a time.

With legibility

A short map sits beside the config

  • Here are the packages, here's what each owns, here are the arrows for which may depend on which. The agent reads it first — it's small, findable, written for a reader.
  • It places the computation in finance, exposed through the one edge reporting is allowed to use. The import direction is right on the first attempt.
  • The lint config still stands behind the map as the sensor; it just never has to fire.

The guide got there first, so the boundary never had to be discovered by colliding with it.

Enforcing a boundary and making it legible are two different jobs — you want both

The lesson the example carries: a config that fails the build is a sensor — it tells the agent it was wrong, after the fact. A readable map of the same boundary is a guide — it tells the agent what's right, before it acts. Structure that's only enforced makes the agent learn by colliding with it; structure that's also legible lets the agent navigate it. Arrange the repo so the shape is readable, and pair every boundary the config guards with a map the agent can actually read.

05Anti-patterns

  • The buried boundary. The architecture lives only inside a sprawling lint config — enforced, but never stated anywhere a reader learns it first. The agent discovers each rule by tripping it. (Guides — Feedforward · Sensors — Feedback)
  • The bespoke layout. An idiosyncratic structure the agent has no training-data priors for, so every placement is a guess and every convention has to be hand-written to compensate.
  • Scattered conventions. The rules for how the repo is organised spread across a wiki, several docs, and a config, so "where does X go?" has no single answer.
  • The stale map. A layout or boundary map that no longer matches how the code actually works, teaching the wrong structure with the authority of being read first. (Growing the Harness)
  • Grep-the-whole-tree. On a large codebase, leaving the agent to locate every symbol by scanning files one at a time — burning budget on navigation a structural index would hand it for free.
