Drift and Health Sensors

Some decay is caused by no single change, so no single change can catch it. Drift and health sensors run on a clock instead of on a diff — dead-code scans, dependency checks, coverage trends, architecture-drift janitor runs — to catch the rot that accumulates between changes rather than inside one.

Every sensor in the book so far fires on a change — a diff arrives, a check grades it, the trunk stays clean. Powerful, and structurally blind to one entire category of trouble: the rot no single change causes. Dead code that emerged from three perfectly innocent commits. A vulnerability disclosed upstream while your repo sat untouched. Coverage sliding a point a week, never quite enough to trip a gate. No diff is to blame, so no diff-gate ever fires. The fix is almost cheeky in its simplicity: change the trigger from the diff to the calendar.

01The principle

Every sensor so far in this playbook fires on a change. A test, a linter, a type check runs because a diff arrived; it grades that diff and either blocks it or lets it through. That model is the backbone of the harness — but it has a blind spot, and the blind spot is structural: a change-triggered sensor can only catch problems a change causes. Some problems aren't caused by any one change. No diff is to blame, so no diff-triggered sensor ever fires.

The trigger for catching those is not a change — it's time. A drift or health sensor runs on a schedule, out of band from the change lifecycle, and asks a question no single pull request could answer: what has quietly rotted since we last looked? Five kinds are worth standing up:

Dead-code detection

Code nothing calls anymore — a function whose last caller was deleted three changes ago. No single change "introduced" it; it emerged from their sum. A scheduled scan finds the orphans and proposes their removal.

Dependency & vulnerability scanning

A library gets a CVE disclosed upstream, months after the code that uses it merged green. Nothing in your repo changed — the risk appeared from outside. A cadence scanner re-checks the world on a clock.

Test-quality trend monitoring

Coverage and mutation score as a direction over time. A slow slide is invisible to any one change, each of which moves the number too little to gate on. Tracking the trend turns a slide into a visible line.

Architecture-drift scans

The codebase diverging from its intended shape — boundaries blurring, a module accreting responsibilities. A scheduled "janitor" run scans for the drift and proposes fixes, so entropy gets a standing counter-force.

Spec-drift detection

The spec chapter tells you to audit spec and code for drift; this scan is the mechanism. On a schedule — or triggered in CI when either side changes — compare the spec's REQ-xxx and AC-xxx ids against the tests and code that claim to implement them: every requirement traces to at least one test, every scenario-tagged test traces back to a requirement, and the API surface matches the spec's interface contracts.

Five sensors whose trigger is the calendar, not a diff

The drift that last one catches is exactly the kind no diff review sees: an endpoint returning fields the spec never declared, a required field silently dropped in a refactor, a requirement whose only test was deleted three changes ago — each side still locally green, the contract between them quietly void.

A sixth member you've already met: observability — runtime sensors watching production. It belongs to this same family, but it runs continuously on live traffic rather than on a schedule against the repo, so it has its own page. This page is about the scheduled scans of the codebase itself.

02Why it works

No diff is responsible, so no diff-gate can help. Picture dead code: change A adds a helper, change B is the last caller, change C deletes B's caller. After C, the helper is dead — but C never touched the helper. There is no diff whose review could have caught it. The same logic holds for an upstream CVE (no local diff at all), for an eroding coverage trend, and for architecture drift. When the cause is cumulative or external, the only sensor that can see it is one whose trigger is also not a single change.

When the cause is cumulative or external, the only sensor that can see it runs on a clock, not on a diff.

A trend says what a snapshot can't. A single coverage number is nearly meaningless — 80% of what, and is that rising or falling? The same number measured every week draws a line, and the line is the signal: flat is fine, climbing is great, and a steady decline is a warning that test-writing is falling behind code-writing well before any individual change would trip a gate.

One-shot is a photo; a trend is the weather — the slide is invisible until you draw the line

This is where the AI-native version earns its keep. A drift scan that only produces a dashboard produces nothing — someone has to read it, and nobody does. But the janitor doesn't have to stop at a report: a scheduled agent run can scan for the drift and draft the fix — open the PR that deletes the dead code, bumps the dependency, or re-draws the leaked boundary — so the finding arrives as reviewable work. The agent proposes; the gate and a human still dispose.

Cheap insurance against silent decay. None of these sensors is on the critical path of a change, so none of them slows anyone down. They run while you sleep. The thing they buy is that the codebase's slow problems announce themselves on a cadence instead of surfacing all at once, years later, as "why is everything like this?"

03How to apply it

  • Run them on a clock, out of band. A nightly or weekly job — never a pre-commit or pre-push hook. These scans are slow and their findings aren't a single author's fault, so putting them on the change gate would block the wrong person for a problem they didn't cause.
  • Make every finding land as action, not a dashboard. Wire each sensor to produce work: the dependency scanner opens a bump PR, the dead-code scan opens a deletion PR, the drift scan files a proposed diff. A finding with an owner gets fixed; a finding on a dashboard gets admired and forgotten.
  • Track trends, not snapshots. Record coverage and mutation score over time and look at the slope. A single threshold gate on coverage invites gaming with low-value tests; a trend line tells you the honest direction. On cadence: the full mutation run is a scheduled, trend-tracking job — far too slow for any change gate — while the incremental runs scoped to changed code live in the change loop. Same sensor, two triggers: the diff checks today's change, the clock checks the direction.
  • Classify every spec change before it merges. The spec-drift scan has a diff-triggered companion: drift cuts both ways, and a change to the spec itself moves the very contract the scan measures against. So when a spec changes, classify the change — additive (a new requirement), compatible (clarifies without changing promised behaviour), breaking (changes what an existing requirement promises), or ambiguous (can't tell) — and let additive and compatible flow through the normal gate while breaking and ambiguous require a human sign-off before merge. An agent can propose the classification; a person confirms the two kinds that redefine the contract.
  • Keep the non-deterministic scans advisory. A janitor that auto-merges its own architecture "fixes" is a gate making semantic calls it isn't qualified to make unsupervised. Let the agent propose and route it through the same review as any other change.
  • Budget time to act, or don't run the scan. A scanner whose PRs pile up unmerged for months is worse than none — it manufactures noise and trains the team to ignore a whole category of signal. Schedule the acting, not just the scanning.
  • Watch for the silent scan. A drift sensor that never finds anything is either good news or a sensor that isn't actually detecting. Periodically confirm it can still fire.
  • Don't: put these on a git hook; let findings accumulate on a dashboard with no owner; gate hard on a coverage number instead of watching the trend; auto-merge a janitor's semantic fixes; or run a scan you've no intention of acting on.

04In practice

A team ships steadily for a year. Every change is verified, gated green, merged on a short-lived branch. The change lifecycle is healthy. And yet.

No drift sensors

A year of silent decay, billed in one lump

  • A JSON library used since month one has a CVE disclosed in month nine — no diff fired, so nobody noticed.
  • Three helpers' callers were refactored away; a whole module is reachable by nothing.
  • Coverage slid from 84% to 71% one imperceptible drop at a time.

It all surfaces at once in month twelve — a security audit, a refactor tripping over dead code, a senior engineer asking why the suite feels thin. None of it was any one diff's fault.

The scheduled jobs

Nothing allowed to accumulate

  • The dependency scanner opens a bump PR the morning the CVE drops — reviewed and merged before lunch.
  • A weekly dead-code scan opens a small deletion PR each time an orphan appears.
  • The coverage trend ticks down in month three — early enough to reverse while the slide is still gentle.

A monthly architecture janitor proposes the boundary split a human reviews and merges — nothing surfaces in one lump, because nothing accumulated silently.

The decay existed in both worlds — the difference was whether anything was looking between the changes

The lesson the example carries: the change lifecycle, however healthy, is structurally blind to problems no single change causes; drift and health sensors are the clock-driven counterpart that catches exactly those — and in an AI-native team they don't just report the rot, they open the PR that fixes it.

05Anti-patterns

  • The dashboard nobody reads. A drift report, a coverage graph, a vulnerability list — generated on a schedule, owned by no one, actioned never. A sensor whose output doesn't become work is just decoration. (Failure modes)
  • The snapshot mistaken for a trend. Running mutation testing or coverage once and treating the number as settled, when the signal that matters is the direction it moves. (Behaviour harness)
  • The auto-merging janitor. Letting a non-deterministic drift scan merge its own semantic "fixes" with no review — a gate that can't be argued with making architectural calls unsupervised.
  • The bot whose PRs pile up. A dependency or dead-code scanner whose output is never triaged, so the unmerged PRs become noise and the team learns to ignore the channel — the alert that cried wolf, in PR form.
  • Drift on the diff gate. Bolting a slow, cumulative-by-nature scan onto a pre-push hook, so it blocks the wrong author for rot they didn't introduce — and gets disabled with --no-verify by the end of the week.
