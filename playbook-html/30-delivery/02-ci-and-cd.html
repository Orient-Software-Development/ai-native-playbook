CI and CD

Keep two jobs separate: CI verifies every change and is the authoritative gate that decides what may merge; CD takes the already-verified result and releases it. Conflate them and you get the worst of both — deploy trouble blocking good merges, or unverified code shipping.

Trunk-based development leans its entire weight on one assumption: that something guards the trunk and won't let a broken change land. This page is that something. And the headline lesson is a seam most teams smear together — "CI/CD" is really two jobs that should never share a pipeline. One decides what may merge; the other ships what already passed. Blur them and you get the worst of both worlds: good code frozen by a deploy hiccup, or unverified code sailing out the door with a reassuring green badge.

01The principle

Trunk-based development only works because something stands at the trunk and refuses to let a broken change in. That something is the CI gate, and this page is about what it is, what it is not, and how to keep it both trustworthy and quick.

Two distinct jobs hide under the single phrase "CI/CD," and the whole lesson is to keep them apart:

  • CI — continuous integration. On every push and pull request, an automated pipeline verifies the change: build it, lint it, type-check it, run the layered test suite. CI answers one question — is this change safe to merge? — and its verdict is the authoritative entry condition for the trunk.
  • CD — continuous delivery/deployment. Once a verified change is on the trunk, CD takes that exact artifact and moves it out to environments. Delivery means the artifact is always ready to release at the push of a button; deployment means it goes out automatically. Either way, CD's input is something CI already blessed.

The rule is a clean seam between them: CI gates the merge; CD gates the release. They run on different triggers, answer different questions, and fail for different reasons — and you keep them that way on purpose.

02Why it works

The seam matters because conflating the two breaks in both directions, and each direction is a familiar outage.

Bolt deployment onto the merge gate, and deploy problems block good code. If "deploy to staging" is a required step of the same pipeline that decides whether a PR can merge, then the day staging is down — a cloud hiccup, an expired credential, a full disk — nothing merges, even though every change is perfectly correct and verified. You've coupled "is this code good?" to "is the deploy target healthy?", and the second question has nothing to do with whether the code should land.

Bolt verification onto the release path — or skip it to unfreeze — and unverified code ships. The usual sequel to the freeze above is someone making the deploy step non-blocking under pressure, and quietly loosening the test gate along with it "to get things moving." Now the wall has a hole: a change can reach production without CI's verdict behind it. The gate that the whole trunk discipline depends on is exactly as strong as its strictest enforced check.

The gate is also what makes agent throughput safe. When agents are opening many small PRs a day, no human can be the merge gate — there's too much, too fast, and "looks fine" is the least reliable signal on agent code. The automated gate is the thing that scales: it decides merge-readiness deterministically, every time, no matter who or what wrote the change.

But a strict gate that's slow gets routed around. An agent iterating on a PR pushes often — and if every push triggers the full integration-and-e2e suite, the CI queue clogs, feedback takes ages, and people start merging around the slow gate. A gate everyone learns to dodge is no gate at all. So the gate has to be both strict and fast, which is what draft-aware gating buys you.

While a PR is a draft

Run only the fast checks — lint, types, unit tests — so an agent pushing repeatedly gets feedback in seconds. You stop paying for the heavy suite on every work-in-progress push.

When it's marked ready

Run the full suite — integration, e2e, performance — and require it green before merge. The strict checks still gate the merge; you just moved the cost off the iteration loop.

Draft-aware gating: cheap on drafts, full on ready — strict and fast

03How to apply it

  • Draw the seam: CI decides merge, CD decides release. Put build, lint, type-check, and the test pyramid in the pipeline that gates the PR. Put deploy-to-environment in a separate pipeline that triggers off a merged trunk. A deploy failure should page whoever owns the environment — never block an unrelated, correct change from merging.
  • Make CI the one authoritative, required, un-bypassable gate. Every must-not-merge check lives here as a required status, not in a skippable local hook. If it isn't enforced in CI, it isn't enforced.
  • Gate on drafts cheaply, gate fully on ready. Use draft-aware gating so feedback is near-instant while iterating, and the heavy suite runs the moment the PR is marked ready for review.
  • Promote the same artifact; never rebuild to ship. CD should deploy the exact build CI verified. Rebuilding reintroduces the question CI already answered, and a different build is a different, unverified thing.
  • Scope the gate to the change. A docs-only PR shouldn't drag the whole e2e suite; let the pipeline skip the executable gates when there's nothing for them to catch.
  • Don't: make deploy a required step of the merge gate; loosen the test gate to work around a deploy outage; run the full heavy suite on every draft push until the queue clogs; or rebuild the artifact for production instead of promoting the verified one.

04In practice

A team sets up "a CI/CD pipeline": one job, triggered on every PR, that runs build → test → deploy-to-staging, and the PR can't merge until the whole job is green.

One conflated job

build → test → deploy, all gating the merge

  • Direction one: staging's database goes down for maintenance; the deploy step fails, so the pipeline is red, so no PR can merge — including three correct slices that never touched staging.
  • Direction two: to unfreeze, someone marks deploy non-blocking and — in the same harried edit — flips the test job to non-required.
  • That afternoon an agent's PR with a real failing integration test merges anyway.

The trunk froze on an outage that wasn't a code problem — then a bug shipped behind a green checkmark because the gate that would have caught it was no longer required.

Split along the seam

CI gates merge · CD ships after

  • CI — build, lint, type-check, test pyramid — runs on every PR and never touches an environment, so a staging outage can't freeze the trunk.
  • CD — deploy to staging, then production — runs after merge; if it fails it pages the environment owner and merges keep flowing.
  • Draft-aware gating keeps each draft push fast and runs the full suite the moment the PR is ready.

The gate is strict (nothing merges unverified), fast (drafts don't pay the heavy suite), and decoupled — deploy trouble never blocks a good merge.

"CI/CD" is two jobs, not one — and the freeze and the shipped bug both come from blurring them

The lesson the example carries: CI is the authoritative answer to may this merge? and must be strict, required, and fast enough that nobody dodges it; CD is the path that ships what CI already blessed and must be free to fail without freezing the trunk. Keep the seam and the trunk stays both releasable and unblocked; blur it and you get frozen merges, shipped bugs, or both.

05Anti-patterns

  • The merge gate that deploys. Deployment wired as a required step of the gate that decides merge, so an environment outage freezes the trunk for changes that are perfectly correct. (Failure modes)
  • The release path that skips CI. A deploy route — or a loosened gate under pressure — that lets code reach production without CI's verdict behind it. The wall with a hole ships bugs with a green badge.
  • The slow universal gate. Running the full heavy suite on every draft push until the queue clogs and the team starts merging around it — a strict gate made worthless by being slow.
  • The rebuild-to-ship. Compiling a fresh artifact on the way to production instead of promoting the one CI verified — shipping a different, unverified thing than the one that passed.
