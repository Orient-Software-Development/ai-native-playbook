Scorecard Template & Scoring Prompt

The two artifacts that drive the scoring chapter: the scoring prompt you hand a coding agent, and the scorecard it fills in — five layers, each number backed by a command you can re-run. Point it at your own repo and get a map of where the harness is blind.

These templates are the fillable companions to Scoring an Existing Harness. The rubric grades capabilities, not specific tools, and is model-agnostic by design — run it with Claude or Codex, or both and merge the evidence. The whole discipline rests on one rule: every score cites a command, a file:line, or a GitHub setting — no unsourced numbers.

Start here instead — the skill-driven starter

The templates below are the manual fallback. For most teams the better starting point is the skill-driven Harness Adoption Starter — point an agent at its assess skill and it detects your stack, scores the five layers, and generates a fitted scorecard rather than making you fill one in by hand. It ships per-tool entry points (Claude Code, Cursor/Copilot/Codex, or a paste prompt for chat agents with no repo access). Reach for the raw prompt and blank scorecard only when you can't run an agent against the repo.

01How to use it

  • Hand the prompt to an agent with read access to the repository (§04 below). It runs discovery first, then measures each layer, then fills in the scorecard.
  • It produces a completed scorecard — five scores 1–10, each with the evidence behind it and a ranked list of what to build next. It's an assessment only: the agent modifies no source outside the scorecard it writes.
  • Keep every scorecard, dated. The first run is a baseline; the value compounds on the second, when you diff it and see what moved, what regressed, and which recommendation was actioned.

02The five-layer rubric — band anchors

Score each layer against these anchors. When a repo sits between two bands, the evidence decides — cite it. Read every score against the harnessability ceiling: an untyped, boundary-less repo cannot top-band Maintainability or Architecture no matter how disciplined the team.

Five layers × five bands — the anchors that turn a gut feeling into a comparable number

Scoring discipline — non-negotiable

Every score cites a command, file:line, or GitHub setting. Every count is measured over tracked source (git grep, not a store-walking grep -r) — state the command. Discover the repo's own idioms; don't grep for another repo's conventions. An advisory check (continue-on-error, un-required, unprotected branch) is not a gate — score it as a report. Read every score against the harnessability ceiling.

03What the scorecard captures

The filled-in report (one Markdown document) walks these sections — each layer score backed by the exact commands and their output:

  • §0 · Harnessability — static types, module boundaries, framework, test coverage, and the stack. Scored first because it sets the ceiling; not averaged into the layers.
  • Summary scorecard — the five scores, with (Prev) and Trend columns once a previous scorecard exists, plus a 2–4 sentence headline.
  • §1–§5 · the five layers — Feedforward, Maintainability, Architecture fitness, Behaviour, Inferential. For each: what's present/strong, what's missing/weak, and the reproducible evidence. The Maintainability integrity check (count over tracked source, never node_modules) is run explicitly.
  • §6 · Status of prior recommendations — on delta runs, what got done since last time.
  • §7 · Recommended actions — ranked by impact-to-effort, each naming the exact change, an effort estimate, and why now.
  • §8 · Open questions — ambiguities the scan surfaced but couldn't resolve.
  • Method note — exactly what was run, any prior figure corrected, and the statement that no source outside the scorecard was modified.

04The scoring prompt

Hand this to a coding agent with read access to a repository. Copy everything in the block below as the agent's instruction — it produces a completed scorecard in the structure above. 

You are auditing the **harness** of the repository you have access to — everything
that steers and grades a coding agent *except* the model itself. Produce a completed
scorecard. Score five layers 1–10. This is an assessment only: do not modify any
source file outside the scorecard you are writing.

Read "Harness Engineering" and "Scoring an Existing Harness" first if available —
they define the five layers and the scoring discipline.

## Phase 1 — Discover (before scoring anything)
Establish what *this* repo is, and how it realises each harness capability. Do not
assume another repo's idioms. Find:
- Stack & harnessability: language(s), static-typing state, framework, build system,
  CI provider, test runner. Clear module boundaries? Does a suite exist and run?
  Record in §0 — it sets the ceiling.
- The repo's own conventions: instruction file(s) (CLAUDE.md, AGENTS.md,
  .cursorrules, copilot-instructions.md), the spec/ADR/docs corpus, lint/format/type
  config, CI workflows, test layout, branch-protection / rulesets (via gh if present).
- How each capability is realised here. The rubric grades *capabilities*, not tools —
  map each to this repo's actual mechanism (or confirm its absence).

## Phase 2 — Measure (evidence first, score second)
For each layer, gather reproducible evidence, then score against the band anchors.
Measurement integrity (non-negotiable):
1. Tracked source only. Every count over version-controlled source — git grep /
   git ls-files, never a store-walking grep -r into node_modules/vendor/build output.
   Write the exact command into the scorecard.
2. No unsourced scores. Every score cites a command, file:line, or GitHub setting.
3. Advisory ≠ gate. continue-on-error, not-required, or unprotected-branch checks are
   reports, not gates. Verify what actually blocks a merge (protection AND rulesets).
4. Committed vs lived. For inferential especially, distinguish what the tree enforces
   from what merely runs in org settings. A gh pr list --json reviews pass over the
   last ~20–30 PRs shows which AI reviewer is active. Flag org-only controls as fragile.
5. Discover the real id schemes. Find the repo's actual scenario/test id pattern (it
   may be SCN-<AREA>-<n>, a ticket ref, a describe() tag). State the pattern you used.

## Phase 3 — Score and report
Fill in: §0 harnessability + ceiling read; the summary scorecard (five scores, trends
only if a prior scorecard exists); §1–§5 each with present/missing/evidence; §7 ranked
actions naming the exact change, effort, and why now; §8 open questions; a method note.

Calibration: read every score against the §0 ceiling; a layer scoring 1 means *absent* —
say so. Prefer the blunt reproducible fact over the sophisticated guess. If unsure
between two bands, cite the evidence and pick the lower.

Output the completed scorecard as a single Markdown document. Nothing else.

Model-agnostic by design — run it with either model, or both and merge the evidence

That's the whole kit. The chapter that explains the why behind it — and how to read a finished scorecard — is Scoring an Existing Harness; the five-layer model it grades against comes from Harness Engineering.
